The Operating System must:
1. Interleave the execution of multiple processes
2. Allocate resources to processes
3. Protect the resources of each process
4. Enable sharing among processes
5. Enable synchronization among processes

A *process* is: 
- A program in execution
- An instance of a program running on a computer
A *process* is comprised of: (first 4 are address space)
1. Program code (possibly shared)
2. A set of global static data
3. User stack (for function calls & local variables)
4. User heap (for dynamic allocations)
5. Process Control Block (PCB)
- Attributes describing ALL required info about the process
*Process Control Block* include WHAT?
- Process Info
  - Identifier, Priority, Parent ID,…
- Scheduling Info
  - Thread Control Block(s) TCBs (CPU Reg’s, State, …)
- Memory Info
  - Tables, Working Sets, …
- I/O Info
- Files Info
- Accounting Info
## 5-State Process Model
**New** : Process is created, not loaded in memory
-admit-> **Read** : Loaded in memory, number of them is limited by OS
-dispatch-> **Running** : Moved to CPU to execute
       -release-> **Exit** : Completed to aborted
       -event wait-> **Blocked** : wait on a request (I/O, OS, resource)
**running $\rightarrow$ ready**(timeout) : reached max allowed time, preempted to allow high priority process, background process
**blocked $\rightarrow$ ready**(event occurs) : event has happened
ready to exit : terminated by its parent

## 7-State Process Model
![[Pasted image 20261006131650.png]]
**Blocked/Suspend** : Process is in secondary memory and waiting for an event
**Ready/Suspend** : Process is in secondary memory and ready to execute

**blocked$\rightarrow$blocked/suspended** : If no ready processes, swap-out one to make room for a ready one
**Block/suspend$\rightarrow$ready/suspend** : When the waiting-event is occurred
**ready/suspended$\rightarrow$ready** : When no ready processes or it's a higher priority
**Ready$\rightarrow$ready/suspended** : Not common (blocked is preferred). Needed if it's the only way to free a sufficiently large block of RAM or high priority.
**Run$\rightarrow$ready/suspended** : Not usual situation, done to free room for higher priority
**New$\rightarrow$ready/suspended** : To maintain a large pool of non-blocked processes while no room in RAM
## Dual Mode Switching
**Switching Models**
![[Pasted image 20261006134015.png]]
### **How to switch**
- Interrupts invoked with interrupt lines from H/W devices (Interrupts)
- OR generated by S/W (System Calls) OR caused by it (Exceptions)
- *Interrupt controller* chooses interrupt request to handle using:
	- *Interrupt Mask* enables/disables Interrupts ONLY
	- *Priority encoder* picks highest enabled interrupt
	- Interrupt identity specified with ID line
then send it to *CPU* which checks *Interrupt Descriptor Table (IDT)* for the suitable handler for each interrupt
- CPU can disable H/W Interrupts with internal flag (sti( ) – cli( ) instr)
- *Non-Maskable Interrupt* line (NMI) can’t be disabled
	- Caused by H/W failure

**Interrupt Descriptor Table (IDT)**:
Table of 256 8-byte entries. Each specifies a protected entry-point(location for the handler function) into the kernel.
Located anywhere in memory (that's why we got to have a register to points to it )
*IDTR register*: Stores address & size of current IDT.
each 8-byte has:
- *offset* -> function entry-point
- *bit 40* -> 0 = interrupt gate; 1 = trap gate

#### **Entry Mechanism**
**User to Kernel**
*Old Stack*(SS:ESP) and *Old Instructions*(CS:EIP) are pushed by *Hardware* from User Stack to Kernel Stack
*New State*:
- SS:ESP -> from Task Stage Seg(TSS)
- CS:EIP -> from IDT
- EFLAGS -> interrupt gate : clear
**Kernel to Kernel**
Only *Old Instructions* are pushed, same stack
CS:EIP -> from IDT

#### **Return Mechanism**
**Where do we return?**
- *Hardware Interrupts* -> old CS:EIP points past last completed instruction.
- *System Call (INT 30, ... )* - > old CS:EIP points past instruction causing system call
- *Exceptions/Faults (page fault, GPF, ... )* -> old CS:EIP points to instruction causing exception
- *Aborts (hardware errors, bad system table vals...)* -> uncertain CS:EIP, serious problems, CPU confused

**Example: Interrupt Cycle for System Calls**:
- Causes a **trap**, which **automatically** do the following by **H/W**
    1. Switch to the kernel mode
    2. Switch to Kernel Stack (SS:SP from Task State Seg **TSS**)
    3. Save flags, return address & old stack
    4. Look in Interrupt Descriptor Table (IDT)
    5. Jumps to the **syscall handler** in the kernel.
- The **syscall handler** (OS) do the following:
    1. **Save caller's state** (CPU Reg's) so it can restore control to the user process later.
    2. Check the **system call number** (Typically, a number associated with each system call)
    3. Call **associated function** that serve the given system call and pass to it the caller's **parameters**
    4. After finish, **restore** caller's state (CPU Reg's)
    5. use **iret** (interrupt return) instruction to **return** to user mode.
        - Restore flags, return address & old stack
To pass parameters u pass them to *Registers*

## Concurrency & Locks
![[Pasted image 20261013220010.png]]
**Non-Determinism**: Scheduler can run threads in any *order* and can switch threads at any *time*
**Main Problem**: Sharing of Global Resources (H/W or S/W)
ex: In ATM server: you & your brother deposit 1000$ & 2000$ in same account at same time. What will be the amount of money added to the account? 1000, 2000 or 3000?
**Critical Section**: Protect it!! used by 1 only. Don’t leave till finish
Any Shared Resource MUST be PROTECTED by *Critical Section*
``` c
Lock lk
Acquire(&lk)
# Proccessing
Release(&lk)
```
### **Implementation**
- Locks provide two atomic operations:
	- `Lock.acquire()` – wait until lock is free; then mark it as busy
		After this returns, we say the calling thread holds the lock
	- `Lock.release()` – mark lock as free
		Should only be called by a thread that currently holds the lock
		After this returns, the calling thread no longer holds the lock
#### **Locks: Implementation**
##### **First one**
On a uniprocessor, can avoid context-switching by disabling interrupts
Consequently, naïve Implementation of locks:  
```
LockAcquire { disable Ints; }  
LockRelease { enable Ints; }
```
Problems with this approach:
- *Can’t let user do this! Consider following:*
	 ```
	 LockAcquire();  
	 While(TRUE) {;}
	 ```
- *Real-Time system—no guarantees on timing!*
	Critical Sections might be arbitrarily long
- *Doesn’t work well on multiprocessor*
	Disabling interrupts on all processors requires messages and would be very time consuming
##### **Second one (SpinLock)**
Usually used for *short-time critical section*
*Exchange Instruction* -> Exchanges the contents of a register with a memory location
The entire function is carried out atomically; not subject to interruption (i.e. indivisible). -> one at a time

*Busy-Waiting*: thread consumes cycles while waiting
*Positives*:
- Machine can receive interrupts
- User code can use this lock
- Works on a multiprocessor
- No System Calls at all
*Negatives*
- This is very inefficient as thread will consume cycles waiting (busy-waiting)
- Starvation is possible
	when a process leaves a critical section, selection of a waiting process is arbitrary
	Some process could indefinitely be denied access.
- Cache coherence issue in multi-cores
	always read-write while waiting (exchange 1 with 1) is useless, high traffic on cache buses to ensure data consistency
- Priority Inversion: If busy-waiting thread has higher priority than thread holding lock -> no progress!
